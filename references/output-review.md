# Outputs and review

## Output schemas

Use only the schemas needed for the requested scope. Combine registers when doing
so preserves clarity; do not produce an excessive number of documents.

| Output | Minimum fields |
|---|---|
| Scope summary | Entity, activities, items/information, people, locations, systems, jurisdiction basis, exclusions with rationale, unresolved questions |
| Document register | Document ID/title, purpose, canonical version, owner, status, dependencies, requested action |
| Risk profile | Activity, exposure scenario, known safeguards, supporting facts, remaining risk, proposed treatment; include ratings only with a stated method |
| Source traceability | Topic, precise source/citation, authority type, edition/effective date, URL/access date where applicable, applicability rationale, document/section, verification status |
| Adaptation matrix | Existing document/section, export topic/source, existing coverage, gap, treatment, proposed wording/change, owner, status |
| Change summary | Document/version, changed section, material change, reason, affected documents, approval needed |
| Decision/action list | Issue, decision or implementation action, owner, status, dependency, evidence needed, date if provided or proposed |

Use adaptation treatments consistently: retain; cross-reference; revise; create;
not applicable with rationale; clarify. Keep legal-source validation separate from
coverage and operating-evidence status. A missing operating record does not erase
a documented governance provision. A written provision does not prove execution.

## Document structure

For a policy, include purpose, scope, definitions, management commitment, roles and
authority, applicable obligations, policy provisions, exceptions/escalation process,
records, review, and approval fields as appropriate. Do not create a company
exception process that purports to waive law or authorization conditions.
For a procedure, include trigger, actor, inputs, steps, decision points, approval,
escalation, and record. For a plan, explain organization, responsibilities, resources,
implementation, and maintenance. In an SSP, describe confirmed implementation and
identify planned changes distinctly.

## Final review

1. Check scope and the selected workflow against the actual request.
2. Check each legal assertion against the applicable current primary source; flag
   unresolved currency or interpretation rather than silently certifying it.
3. Check sources and document references for accurate identifiers and locations.
4. Check that agency guidance, vendor descriptions, and company choices are labeled.
5. Check that applicable NISPOM, ITAR, EAR, and cybersecurity topics remain distinct.
6. Check authorization scope, access assumptions, and data flows against supplied facts.
7. Check document owners, procedures, forms, retention, and reporting provisions agree.
8. Check SSP changes preserve confirmed facts, canonical location, and required granularity.
9. Check new revisions are not represented as already approved or implemented.
10. Check requested formatting and visual quality using the relevant artifact skill.

Report completed drafting, material changes, and remaining decisions or actions.
Avoid a blanket compliance verdict or new approval gate for routine drafting.
